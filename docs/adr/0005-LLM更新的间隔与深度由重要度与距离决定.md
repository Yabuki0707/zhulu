# LLM 更新的间隔与深度，由角色重要度与距离决定

`设计笔记01` §6 曾把 `需求文档` §8 的「按日历频率驱动」改为「**按需驱动**」，`设计笔记02` §3 又立了 T1／T2／T3 三道**事件闸门**——两处都把「LLM 什么时候更新」从角色自身的优先度上挪开，交给「有没有事件」。

需求方定：**回到角色身上。** 由「角色重要度 × 距离 × 投入度」算出 Priority，Priority **同时定两件事**——**间隔**（多久更新一次）与**深度**（这次更新到什么程度）。两者是两个独立旋钮（`需求文档` §8.1）。

事件不另立闸门：`EventBoost` 已经把「有事发生」折算成 Priority 的瞬时抬升，事过自然落回原档。

## Considered Options

- **事件闸门（T1／T2／T3）单独立规**：否。闸门问的是「有没有事」，该问的是「这个角色离玩家多近、多要紧」。远处要人的日常也得照推，近处路人的流水也没必要写——这只有 Priority 答得了。
- **只按距离、不按重要度**：否。主角身边一个卖炭翁和一个部将，值得花的钱差着量级。

## Consequences

- `设计笔记01` §6「§8 模拟等级 → 改为按需驱动」那一行作废；`设计笔记02` §3／§5 的闸门降为「Priority 的一个输入」。
- 成本核算的口径从「数每 tick 开了几个槽」改为「数每个 Priority 带上各有多少角色」——可预算、可回归，规模不变性（§8 验收 1）才测得了。
